{% comment %} apps/invoices/templates/invoices/pro_statement.html 20-Template Import, Batch 5 (15 September 2026) — ported from proTemplates.html's "Statement" prototype (tpl-statement). NOT to be confused with the existing account-statement generator (apps/invoices/templates/invoices/statement.html, rendered by pdf_generator.render_client_statement_pdf) — a completely separate, pre-existing feature this batch does not touch; the tier-prefixed key convention (`pro_statement`, this file's own filename) is exactly what resolves that name collision, per template_manifest.py's own docstring. Bold-contemporary design: a persistent, boldly-colored left rail (brand identity, a bold "INVOICE" label, and a QR/"Scan to pay" box), a bordered meta strip, standard items/parties, and a highlighted "Total due" bar. Real, preserved deviation #1: the persistent rail — same pagination- simulation-artifact reasoning as pro_atelier.html/pro_consulting.html/ free_minimal.html; ported via `position: fixed`, repeating on every real page automatically. Real, preserved deviation #2 (a real, deliberate SIMPLIFICATION, not a faithful port): the prototype's own `stm-total-bar` sits OUTSIDE the rail+main grid entirely — a full page-width flex sibling beneath both columns, spanning under where the rail's own colored fill sits too. That shape cannot be safely reproduced here: the rail is `position: fixed` (so it repeats, unconditionally, on EVERY real page — including whichever page the total bar naturally lands on), and a real full-width, non-fixed block appearing later in DOM order would paint OVER the rail's own color/content in that overlapping region on that page, since fixed- position elements do not automatically create an isolated stacking context above later normal-flow content in WeasyPrint. Rather than building and finger-crossing a z-index-flavored fix for a single cell of this template, the total bar here is confined to the MAIN column's own width (starting after the rail, like `pro_editorial.html`'s own `edt-total-bar`) — the real, meaningful part of this deviation (a bold, highlighted total callout distinct from a plain right-aligned totals box) is fully preserved; only the literal full-page-bleed-under-the-rail extent is not. Flagged here as a deliberate, safety-driven choice, not a silently-dropped detail. Real, confirmed WeasyPrint limitation found during this batch's own verification (Part 0/1) — the same one pro_atelier.html's own docstring documents: `.stm-rail-word`'s `writing-mode: vertical-rl` (meant to run "INVOICE" vertically down the rail) is a real "unknown property" in this WeasyPrint version, silently ignored. Fixed the same way: dropped both `writing-mode` and the paired `transform: rotate(180deg)`, rendering "INVOICE" as plain, normally-sized horizontal bold text instead. Deliberately does NOT port paginateItems/computeCapacity/ continuationHeader/.page-badge, or the `pages` array concept itself — same reasoning as every prior batch. {% endcomment %} {% load humanize %}
