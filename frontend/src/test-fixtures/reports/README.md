# Reports test fixtures (Prompt 17)

Tracked on purpose (the `*.test.*` files are gitignored). Every file here was **generated from the real views, serializers
and PDF builders**, not typed by hand: throwaway users were created inside one database transaction, their payments and
expenses were created through the real services (`services.create_payment`, `expense_services.create_expense`, so each
rate is frozen exactly as in production), the real endpoints were called through Django's test client with a real minted
access cookie, the responses were saved, and the transaction was rolled back. The run left the database exactly as it
found it (identical row counts before and after for `payments`, `expenses`, `users`, sessions, audit rows, request-log
rows and exchange-rate snapshots).

The dates are **absolute**: every period starts on `2026-01-01` and ends on `2026-11-09` (the day the files were
generated), except `pnl-multiyear` (`2024-11-01` to `2026-11-09`) and the dated scenarios in `notes.sample.json`, which carry
their own `start` and `end`. Tests must not treat "today" as these values; they use them only for shape, order, text and
money.

Inside the rolled-back transaction, throwaway exchange-rate snapshots were added on the 1st of every month from
2024-11-01 (USD, PKR and EUR; **no GBP**, on purpose) so that payments could be exact, nearby or estimated. GBP rows were
created normally and then updated to `rate_to_usd=None, rate_basis='none', exchange_rate_snapshot=None`: a valid stored state
(a currency for which no rate was ever captured) that the API cannot produce for a new row, so it cannot be generated by
calling the endpoints alone.

To regenerate: run the generator (a Django shell script that builds the same data inside `transaction.atomic()` and raises
to roll back), then review the diff. Do not edit these files by hand.
